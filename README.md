# Transaction Ledger Service

A double-entry ledger service. It holds accounts with balances and moves money between them with transfers. Each transfer records two entries, a debit and a credit, that sum to zero. Balances can never go negative. A retried request never moves money twice, and concurrent transfers never deadlock.

Money is always stored as integer minor units (cents) in `BIGINT` columns, never floating point.

## What it does

- **`POST /transfers`** moves money from one account to another, exactly once per idempotency key.
- **`GET /health`** reports whether the service can reach the database.

There is no endpoint for creating accounts yet; seed them with SQL (see below).

### `POST /transfers`

```http
POST /transfers
Idempotency-Key: 6f1c2a0e-order-1234
Content-Type: application/json

{"fromAccountId": 1, "toAccountId": 2, "amount": 2500}
```

`amount` is in minor units (`2500` = 25.00). The response body is the stored transfer:

```json
{
  "id": "0b6c4f2e-...",
  "idempotencyKey": "6f1c2a0e-order-1234",
  "fromAccountId": 1,
  "toAccountId": 2,
  "amount": 2500,
  "createdAt": "2026-10-04T21:30:00.123456Z"
}
```

| Situation | Status |
|---|---|
| New transfer | `201 Created` |
| Same key, same parameters (a retry) | `200 OK`, with the original transfer |
| Same key, different parameters | `409 Conflict` |
| Insufficient funds, or unknown account | `422 Unprocessable Entity` |
| Missing key, non-positive or fractional amount, same account twice | `400 Bad Request` |

Errors are returned as [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details.

A rejected transfer rolls back completely, so it doesn't use up its idempotency key. A client can top up the account and retry with the same key.

## Stack

- Java 21, Spring Boot 3, Maven (via the included wrapper)
- PostgreSQL 17
- Plain JDBC (`JdbcTemplate`), not JPA. Ledger writes need explicit SQL, and the schema is owned by migrations rather than generated by an ORM.
- Flyway for schema migrations
- Testcontainers for integration tests against real Postgres
- Docker Compose for the local database

## Running locally

**Prerequisites:** Java 21 and Docker.

```sh
# 1. Start Postgres
docker compose up -d

# 2. Start the service (applies Flyway migrations on startup)
./mvnw spring-boot:run
```

The service listens on `http://localhost:8080`. If port 5432 is already taken, pick another port and pass the same value to both commands:

```sh
POSTGRES_PORT=5433 docker compose up -d
POSTGRES_PORT=5433 ./mvnw spring-boot:run
```

Seed two accounts and make a transfer:

```sh
docker compose exec postgres psql -U ledger -d ledger \
  -c "INSERT INTO accounts (name, balance) VALUES ('alice', 10000), ('bob', 0) RETURNING id, name, balance;"

curl -i -X POST localhost:8080/transfers \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-1' \
  -d '{"fromAccountId": 1, "toAccountId": 2, "amount": 2500}'
```

On a fresh database the accounts get IDs 1 and 2. Otherwise, use the IDs that the `INSERT` printed.

If you run the same `curl` again you get `200` with the same transfer, and no money moves. If you change the amount but keep the key, you get `409`.

To stop the database, run `docker compose down`. Add `-v` to also delete its data.

## Running the tests

```sh
./mvnw test
```

Docker must be running. The tests don't use the Compose database: Testcontainers starts a throwaway Postgres 17 container, Flyway migrates it, and the container is removed afterwards.

| Test class | Covers |
|---|---|
| `LedgerSchemaTest` | Database rules on their own: the balance CHECK constraint, entries summing to zero per transfer, entries being append-only, foreign keys |
| `TransferControllerTest` | `POST /transfers` end to end: replays, `409` on a reused key, concurrent requests with the same key, insufficient funds, input validation |
| `ConcurrentTransferTest` | 50 simultaneous transfers in both directions between the same accounts: no deadlocks, and balances reconcile against entries |
| `HealthControllerTest` | `/health` and that Flyway ran |

## Design notes

The ledger makes three guarantees. Each is enforced in the one place where it can't be bypassed or raced.

### 1. Balances never go negative: a `CHECK` constraint

```sql
CONSTRAINT accounts_balance_non_negative CHECK (balance >= 0)
```

A debit is a single relative update, `UPDATE accounts SET balance = balance + ? WHERE id = ?`. If it would take the balance below zero, Postgres rejects it with SQLSTATE `23514`, and the service turns that into `422 Insufficient funds`.

**Why the database and not application code?** An application-side check is a read followed by a write, and that races. Two concurrent debits of 80 against a balance of 100 can both read 100, both pass, and leave the account at −60. A CHECK constraint is evaluated on the row being written, while that row is locked, so there's no gap between checking and writing. It also covers every write path: the service, a future batch job, a migration, or someone in `psql`. So the service deliberately does **not** check the balance first. The constraint is the only rule, and the code just interprets its error.

### 2. Each idempotency key moves money once: insert first, then catch the duplicate

`transfers.idempotency_key` has a `UNIQUE` constraint. The service **inserts the transfer row first**, with no lookup beforehand:

1. `INSERT INTO transfers (...)`. If it succeeds, the key is new: update the balances, write the entries, commit, and return `201`.
2. If it fails with a unique violation (`23505`), the key has been used before. The transaction rolls back, and a fresh query reads the original transfer:
   - same accounts and amount: return the original with `200`
   - different parameters: return `409`

**Why not check whether the key exists, then insert?** Two concurrent requests with the same key can both find nothing and both move money. A unique index sees every concurrent request, across threads and across service instances. When a second request inserts a key that another transaction is still writing, Postgres makes it **wait**. It fails only if the first commits, and goes ahead if the first rolls back. The database settles the race, not application timing.

**Why roll back before reading the original?** In Postgres, any error aborts the current transaction, and later queries in it fail. So the service manages the transaction itself (`TransactionTemplate`, not `@Transactional`), lets the failed attempt roll back, and only then reads the stored transfer.

### 3. No deadlocks: lock accounts in ascending ID order

A transfer updates two account rows, and each update takes a row lock. If every transfer locked its from-account first, then A→B and B→A running at the same time could each hold one lock while waiting for the other. Postgres would detect the cycle after about a second and abort one of them.

Instead, the service always updates the **lower account ID first**, whichever direction the money moves. Every transaction acquires locks in the same order, so a cycle can't form, and an opposing transfer simply waits its turn.

**Why application code and not the database?** Lock order is decided by the order in which statements run, and only the application controls that. Postgres can detect a deadlock after it happens, but it can't prevent one. That's why this is the one guarantee that lives in Java, in `TransferService`.

One less obvious detail: inserting a transfer also takes `FOR KEY SHARE` locks on both accounts, because of the foreign keys. Those don't conflict with the `FOR NO KEY UPDATE` lock that a balance-only `UPDATE` takes, so they can't cause a lock cycle either.

`ConcurrentTransferTest` proves the ordering works. It fires 50 transfers in both directions at once. A test-only trigger holds each row lock briefly so opposing transfers are guaranteed to overlap. The test was checked against a version of the code that locks from-account first: it failed with deadlocks on every run.

### Other integrity rules

- **Entries for a transfer sum to zero.** A CHECK constraint only sees one row, so this uses a `DEFERRABLE INITIALLY DEFERRED` constraint trigger. It checks the sum at commit, which lets the debit and credit be inserted as separate statements.
- **Entries are append-only.** Triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on `entries`, since editing a committed entry could unbalance a transfer the commit check already passed. Mistakes are corrected with a reversing transfer.
- **Reconciliation.** `V2__ledger_schema.sql` documents two queries: one finds transfers that don't sum to zero, the other finds accounts whose balance has drifted from their entries. Both should return no rows.
- **No fractional money in requests.** Jackson is configured to reject `"amount": 10.99` instead of silently truncating it to `10`.
